For most of my career, when a tool didn't quite fit, I picked the one that fit best and moved on. In January I needed documentation for our React projects. A few years ago I would have picked VitePress, made my peace with it running on Vue, and shipped. This time I built my own.

Ten months later, Ardo is at version 6.9, every one of our websites runs on it, and I don't plan to settle again.

## Second best used to be the smart choice

I've built JavaScript frameworks since the early 2000s: qooxdoo with 1&1, Unify with Deutsche Telekom, and a long list of smaller open-source projects since. After 25 years you see patterns. You look at a tool and know exactly where it will hurt in two years and how it should have been built.

Knowing isn't building, though. Writing a documentation framework from scratch, with a Markdown pipeline, syntax highlighting, API reference and search, was a team-sized project. So you made the rational call: take the good-enough option and spend your time on the work that pays.

That's what second best really was. Not a lack of taste. A lack of hours.

## What I didn't want

Docusaurus is the obvious answer for React docs. It also carries a lot of history. Version 3.10.2 still builds with webpack by default, and it has grown into a large ecosystem that is hard to slim down from the outside. And it never felt like the right home for a marketing site next to the docs.

The newer tools are lovely, but most of them sit on Astro or Vue. We write React. Our docs need our own components, and so do the landing pages next to them. I didn't want a second stack just for documentation.

So I started small. Something that fit my own projects: MDX in, plain HTML out, and no need to rebuild the same setup for every website we run.

## Every version a little better

The first version worked. After that it was iteration, the way Apple ships iPhones: each one only a step, each one better than the last. Ardo went from version 1 to 6 in nine months, and every major was a real break.

Most of those breaks came from one question I kept asking: what is actually in here, and why?

Ardo started with the usual stack: unified with remark and rehype for Markdown, Shiki for syntax highlighting, TypeDoc for the API reference. All good projects. But I kept running into the same thought. Why pull in a whole library and its dependency tree when I need a tenth of it?

Large, old projects often turn into a monolithic standard. You look at them and wonder how all of that got in, and how nobody minded the project growing like that.

In October, Ardo switched to its own Markdown engine, Ferromark, and its own highlighter, Ferriki, both written in Rust. A week later, TypeDoc was gone and Ardo read the types itself. Each of those pieces became a project of its own. In our [first-render benchmark](https://ferriki.dev/), Ferriki produced HTML 4.2 to 5.5 times faster than Shiki’s WASM build on the same files. One documentation tool turned into a whole family of Rust tools, because every time I dug deeper, I found the next thing I wanted to do properly.

Steve Jobs is often quoted as saying that innovation means saying no to a thousand things. I think about that a lot.

Ardo doesn't need to do everything. What it does has to be right.

"Right" is my right, admittedly. I'm a precision junkie. I want software that behaves the way you expect, that makes simple things simple and hard things possible. Ardo is where I get to hold a tool to that standard all the way down.

## Why now

Something changed this year, and it isn't my taste. When I counted on November 11, about 365 of Ardo’s 787 commits had been written together with an AI agent.

The agent doesn't decide what right means. It doesn't know which dependency annoys me or why a Markdown edge case matters. Twenty-five years of noticing those things do. What the agent changes is the cost of acting on them.

For the first time in my working life, I can take something I don't like and make it better at scale.

## The numbers

I wanted to know whether "lean" holds up, so I installed each tool into an empty project and counted. This is a snapshot of the packages installed by npm on macOS arm64, measured on disk. It does not measure build speed.

| Install                                   | Packages | Size on disk |
| ----------------------------------------- | -------: | -----------: |
| Ardo 6.9                                  |      122 |       124 MB |
| Ardo 2.0.1, January 2026                  |      315 |       212 MB |
| Docusaurus 3.10.2 with the classic preset |    1,278 |       255 MB |
| VitePress 1.6.4                           |      126 |        99 MB |

Ardo installs about a tenth of the packages Docusaurus does, and well under half of what Ardo itself installed in January. VitePress is lighter still. Fair enough: it's the one I would have settled for.

## The honest objection

If you run a team, you're asking a fair question by now: who maintains this when Sebastian loses interest? Docusaurus has Meta and a huge community behind it.

You're right about the community. Open source has a chicken-and-egg problem. Without users, nobody maintains a project, and without maintainers, nobody uses it.

But a big name isn't a guarantee either. Years ago I told people to use Radix UI. Two of the people who built it now work on Base UI. I've watched plenty of React libraries go quiet that once looked like the safe choice.

So here is what I'd point to instead. Ardo doesn't make your content its own. What you bring is React components, Markdown, MDX, and the types in your code. I don't see a lock-in in that. If you decide differently in a year, so be it.

And beyond that, I'm hoping a few people share the taste and want to help.

## The half we never did

There's a German saying: _Tu Gutes und rede darüber._ Do good things and talk about them.

We've always been good at the first half. We'd rather build the next iteration than talk about the last one.

Ardo isn't a business. It's the tool I wanted, built to the standard I care about, and it already runs every site we have. This essay is me starting on the second half.

If you want to try it, hand this sentence to your coding agent, in a fresh repository or one you already have:

```text
Set up Ardo in this repository following https://ardo-docs.dev/llms.txt.
```

It follows Ardo's agent instructions, adapts the tested example, and reports how typecheck, tests, and build went. You review the result like any other pull request.
